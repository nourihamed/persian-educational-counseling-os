# Activity, Class & Assignment Domain Contract — Phase 2

**Status:** DRAFT / NOT APPROVED. Domain model contract only. Synthetic data only (D-014).

## 1. Activity as a shared execution concept

An Activity represents a schedulable/trackable unit of student work. It is not a generic replacement for all educational entities. Specialized records remain authoritative for tests, exams, class sessions, assignments and reviews.

Canonical activity families to map (MVP scope must be confirmed against PROJECT_SCOPE):
- study/reading;
- exercise and problem-solving;
- test/quiz and post-class test;
- exam preparation;
- homework/assignment;
- spaced review;
- summary/flashcard/active recall;
- remediation/weak-topic practice;
- class follow-up;
- daily routine / recurring habit;
- overdue, deferred, static and custom tasks.

The current `activity_kind` list is too narrow to distinguish several approved product behaviors. Before implementation, either extend the controlled taxonomy or model specialized activity subtypes/links. Do not add arbitrary strings or an unrestricted polymorphic `source_type/source_id` pair without referential integrity.

## 2. Activity lifecycle and provenance

- Activity has stable identity, student, Workspace-local owner/creator, kind, title, status, priority, planned duration, source reference and provenance.
- Planned activity and actual execution are distinct. StudySession/execution records capture actual start/end, duration, outcome and evidence.
- Activity may be generated by a PlanItem or created ad hoc; if generated, it retains the exact PlanVersion/PlanItem reference.
- Deferral, overdue carry-forward, cancellation and completion are explicit events with actor, timestamp and reason code.
- An overdue task is not silently duplicated or discarded; carry-forward links the new PlanItem to the prior activity and retains original due date.
- Specialized entities remain authoritative: a TestAttempt belongs to a test definition version; an Assignment belongs to a class/student context; a Review retains its scheduled cadence and outcome.

## 3. Class and session model

- Class is a stable course/group identity within one Workspace.
- A class has one or more subject/curriculum links, instructor/owner, delivery mode and lifecycle.
- Recurring schedule rules are versioned separately from concrete ClassSession occurrences.
- Every session stores start/end UTC plus original local date/time/timezone and recurrence occurrence key; exceptions/cancellations are explicit.
- A ClassParticipant relation links a class to a student/enrollment, with joined/left intervals and status. A class record alone does not grant access to every student in the Workspace.
- Attendance is per participant and session; it must not be inferred from session existence.
- Assignments are scoped to exact class session or class participant/student; due date and timezone semantics are explicit.
- Class visibility requires Workspace membership plus instructor/manager permission or student/guardian relationship; cross-student visibility is not implied by class participation.

## 4. Required schema structures

- Controlled `activity_kind` taxonomy and, where needed, typed link/subtype tables.
- Activity lifecycle/audit events for defer, carry-forward, cancel and completion.
- PlanItem-to-Activity link with version provenance.
- `class_participants` keyed by class/student/enrollment with effective intervals.
- `class_schedule_rules` versioned recurrence definitions.
- `class_sessions` concrete occurrences with unique recurrence occurrence key.
- `class_session_attendance` per participant/session.
- Assignment scope and class/student participant references with composite consistency constraints.

## 5. Required tests

1. Activity kind must be from the controlled taxonomy; unsupported kinds reject.
2. Generated Activity references an exact PlanVersion/PlanItem; ad hoc Activity records provenance.
3. Carry-forward preserves original due date, reason and prior activity reference.
4. Duplicate recurrence generation does not create duplicate class sessions.
5. Recurrence exception/cancellation does not rewrite historical sessions.
6. Class participant must belong to the same Workspace and valid enrollment.
7. Attendance requires a valid class participant and exact session.
8. A student/counselor cannot access another student's class/assignment/attendance outside their relationship permissions.
9. Class membership cannot grant access to counselor-private notes or unrelated student data.
10. Assignment and notification workers re-check participant, permission and ownership generation before delivery.
11. Timezone/Jalali boundary and recurring-session daylight transition behavior is deterministic.

All tests remain NOT IMPLEMENTED / NOT RUN until schema and service boundaries are implemented.
